## Убрали колючки, сделали уровни процедурными, добавили выход и победу

Пользователь: «шипы надо убрать, островки расставить рандомно но так чтобы
герой мог до них допрыгивать. Если собака видит героя она начинает его
преследовать в том числе прыгая по стойкам. В самом труднодоступном месте
расположен выход с уровня... После выхода на новый уровень островки
расставлены уже в другом порядке и так 5 уровней после чего игра
заканчивается победой». Подробности решения — в [[Пушок — гейм-дизайн]]
(разделы «Уровни и прогрессия», «Опасности»).

**Ключевое инженерное решение** — генератор уровня (`systems/levelGenerator.ts`)
не изобретает свою физику: он подбирает высоту и зазор каждого следующего
уступа под `isReachableAtGap`/`gapWindowForStepUp` из уже существующего
`systems/jumpGeometry.ts` (та же физика, что была откалибрована для
фиксированной лестницы уровня 1, см. devlog [[2026-08-05]]). `gapWindowForStepUp` —
новая чистая функция: аналитически решает, при каком диапазоне дистанций
прыжок высотой `stepUp` попадёт на уступ (окно, а не одна точка — высота
сначала растёт, потом падает обратно).

**Баг, найденный на глаз, а не тестами:** после первой реализации на
скриншоте уступы стояли почти впритык (зазор 24px < тайла 32px — читается
как один блок) и почти все на одной высоте. Причина — при генерации «шаг
вверх/вниз, потом обрезать по границам экрана» шаг вниз рядом с полом
почти всегда обрезался в нулевой. Фикс: высота уступа сэмплируется сразу из
полного допрыгиваемого диапазона, а не «шаг, потом обрезка».

**Второй баг, найденный стресс-тестом на 300+ сидах, а не курируемым
набором:** уступы иногда перекрывались — зигзаг по X мог вернуться в
X-область более раннего (не соседнего по цепочке) уступа. Фикс — проверка
`tooCloseToAny` идёт по всем уже поставленным уступам, а не только по
предыдущему; при неудаче генератор перебирает сетку высот и обе стороны
по X, прежде чем сдаться.

**Осознанный компромисс:** в редчайшем структурном тупике (уступ прижат к
краю экрана, единственное доступное направление целиком занято более ранним
уступом — воспроизведено на 1 из ~2500 случайных уровней в стресс-тесте)
генератор жертвует гарантией «дистанция в безопасном окне прыжка» ради
гарантии «уступы не пересекаются» — наслоение блоков было явно запрещено
пользователем, а не побочный эффект для минимизации. Тест на отсутствие
перекрытий прогоняется на 300 сидах × 5 уровней (1500+ проверок) и остаётся
в `test/levelGenerator.test.ts`.

**Собака и прыжки:** `Dog` получила гравитацию и коллизию с платформами
(раньше двигалась только по фиксированному Y пола). `systems/patrol.ts`
пополнился `canSeeTargetAnywhere` (видит цель по X и Y, не только на полу —
заменяет прежний `canSeeTarget`) и `shouldJumpToTarget` (та же
`isReachableAtGap`, что и у генератора уровня). Прыгает собака только в
погоне — патруль остаётся по полу, чтобы не усложнять и без того новую
механику.

**Выход и прогрессия:** `TEX.exit` — плейсхолдер-текстура (арта нет),
рисуется в `PreloadScene` так же, как земля. `GameScene` читает номер
уровня из `init(data)`, оверлап с выходом вызывает `completeLevel()` —
либо следующий уровень (`scene.start('Game', {level: level+1, fish, lives})`),
либо, после 5-го, новая `VictoryScene`. Смерть теперь явно рестартит
**текущий уровень** с сохранёнными рыбками (было: всегда уровень 1 — не
проявлялось при одном уровне, стало наблюдаемо при пяти); это соответствует
уже существовавшей записи в кор-лупе «смерть → рестарт уровня, рыбки
сохраняются».

**Грабли смоук-теста в автоматизированном браузере, снова (см. уже
задокументированные вчера, [[2026-08-05]]).** В этот раз хуже: не только
клавиатура — `document.visibilityState: hidden` полностью останавливает
Phaser'овский игровой цикл (`game.loop.frame` не менялся ни разу за секунду
ожидания, ни клики, ни диспатч клавиш ни на что не влияли, включая уже
запущенные переходы сцен). Прямой JS-диспатч событий в этот раз не помог
вообще ни для пойнтера, ни для клавиатуры. **Рабочий обход, новый:** дёрнуть
Phaser вручную в обход RAF — `game.loop.step(performance.now())` несколько
раз подряд из `javascript_tool`. Так подтверждена вся цепочка логики:
прыжок собаки в погоне (`velocity.y` стал `dogJumpVelocity` при вызове
`dog.update()` с приподнятой целью), переход между всеми 5 уровнями с
сохранением рыбок (`completeLevel()` дёрнут вручную 5 раз подряд), победа
(`VictoryScene`, сейв корректно сброшен на `level: 1`), смерть → `GameOver`
с сохранением уровня и рыбок в `localStorage`. Если в следующий раз смоук
через Browser pane зависнет — сразу проверять `game.loop.frame`, а не
`document.visibilityState` (та проверка тоже не гарантирует ничего в этой
версии окружения).

**Проверено:** `npm run typecheck`, `npm run lint`, `npm test` (91/91,
включая новый `test/levelGenerator.test.ts` на 59 тестов и стресс-проверку
на перекрытия), `npm run build`. Полный интерактивный прогон через реальные
клики/клавиши в Browser pane не удался по описанной выше причине
окружения — логика подтверждена юнит-тестами и прямым вызовом методов сцены
через `javascript_tool`, а не визуальным кликом.

## Автоматический деплой — убрали ручной шаг

Пользователь: «давай исправим блокировку чтобы сборка шла автоматом» — в
ответ на то, что `git push origin main` из Claude Code был денайнут.

**Настоящая причина** (не то, что предполагалось утром): не «харнесс иногда
блокирует», а явная строка `"Bash(git push origin main:*)"` в `deny`
проектного `.claude/settings.json`, перекрывающая более общее `allow:
"Bash(git push origin:*)"` (deny всегда сильнее allow). Убрал эту строку —
пуш в main из агента разрешён.

Заодно убрал и вторую ручную ступень: `deploy-pages.yml` был
`workflow_dispatch`-only, поэтому даже после успешного пуша нужно было
отдельно звать `gh workflow run`. Добавил `on: push: branches: [main]` —
теперь сборка и деплой идут сами следом за пушем, ручной запуск остаётся
как запасной путь. Внутри workflow ничего не менял: `npm run typecheck &&
npm test` перед сборкой остаются как раньше, сломанный код на прод не уедет.

Подробности и план отката — в [[Пушок — техническая архитектура]] (раздел
«Как задеплоить на прод» → «История изменений»).

жалоб — в [[Пушок — техническая архитектура]] («Как задеплоить на прод»).

## Конструктор уровней

Пользователь: «надо сделать констурктор этих уровней, где руками можно
размещать препятствия, награды, опасности. там должна быть сетка доступных
места и перетягивание элементов драг эн дроп». После плана (Before coding
report) уточнил два места: зона патруля собаки — полноценный диапазон
(две ручки), а не точка с фиксированным отступом; плюс отдельная явная
опция прогона проверки проходимости, не только фоновая подсветка.

**Как встроено в архитектуру.** Все уровни строил только процедурный
генератор (`systems/levelGenerator.ts`) — авторских данных не было вообще.
Не стал его заменять: новый тип `LevelData` (`config/level.ts`) и таблица
`CUSTOM_LEVELS` (`config/customLevels.ts`, пустая по умолчанию) — если для
номера уровня там есть запись, `GameScene` берёт её вместо
`generateLevel()`; нет записи — как раньше, процедурно. Откат тривиален
(таблица пустая — ничего в игре не меняется).

**Редактор — не отдельный сайт**, а ещё одна Phaser-сцена (`EditorScene`),
доступна только по `?editor` в URL (`PreloadScene` проверяет
`URLSearchParams`, в обычном меню кнопки нет — dev-инструмент, не для
игроков). Переиспользует те же текстуры и тот же `tileSize`, что и игра.

**Общий источник проверки проходимости с генератором.** Вынес
`ledgesTooClose` (проверка пересечения уступов) и написал новую
`validateLevel` в `systems/levelValidation.ts` — чистые функции, не зависят
от Phaser, используют ту же `isReachableAtGap` из `jumpGeometry.ts`, что и
весь остальной проект. `levelGenerator.ts` теперь импортирует
`ledgesTooClose` вместо своей копии (проверено — все существующие тесты,
включая стресс-проверку на 300 сидов, прошли без изменений после рефактора).

**Баг, найденный собственным тестом сразу после первой версии
`validateLevel`:** первая версия проверяла уступы по возрастанию X, решив
что так «естественно» проверять допрыгиваемость. Тест на уровне из РЕАЛЬНОГО
генератора (тот же самый, что проходит `levelGenerator.test.ts`) неожиданно
провалился — генератор зигзагует по X (может пойти влево после того, как
шёл вправо), так что сортировка по X ломает реальный порядок прыжков.
Исправлено — проверяю в порядке МАССИВА (для генератора это порядок
построения цепочки, для редактора — порядок добавления уступов дизайнером,
это и есть подразумеваемый порядок прохождения).

**Drag-n-drop:** палитра из 3 «штампов» (уступ/рыбка/выход) вверху экрана —
перетаскивание с них создаёт новый объект и не расходует сам штамп. Уже
поставленные объекты тоже перетаскиваются (репозиция) и удаляются (клик —
выделение жёлтым, Delete/Backspace — удаление). Снап к сетке тайлов
(`snapToGrid`). Зона патруля собаки — две белые ручки на полу, между ними
полупрозрачная полоса.

**«Проверить уровень»** красит уступы зелёным/красным по факту
допрыгиваемости и пишет статус-строку с конкретными номерами проблемных
уступов; это происходит автоматически после каждой правки, кнопка — та же
проверка явно + всплывающее подтверждение (пользователь просил именно
«опцию прогона теста», не только фоновую подсветку).

**Экспорт** — JSON в консоль (`console.log`, всегда работает) и в буфер
обмена (`navigator.clipboard`, может не сработать в приватном/неактивном
окне — тогда просто смотреть консоль). Вставляется вручную в
`config/customLevels.ts` под номер уровня. Черновик каждого уровня отдельно
автосохраняется в `localStorage` (`pushok:editor-draft`, отдельный ключ от
игрового сейва) — переключение между уровнями и перезагрузка страницы не
теряют работу.

**Проверено:** `npm run typecheck`, `npm run lint`, `npm test` (101/101,
новый `test/levelValidation.test.ts` на 10 тестов), `npm run build`.
Drag-n-drop живьём в Browser pane не потрогать по той же причине, что и
раньше (`document.visibilityState: hidden` останавливает игровой цикл) —
вместо этого прогнал всю цепочку через `javascript_tool` напрямую по
методам сцены: размещение уступов (недостижимый → красный, допрыгиваемый →
зелёный), перетаскивание ручек патруля собаки, удаление, переключение
уровней с восстановлением черновика из `localStorage`, экспорт (сверил
итоговый JSON в консоли). Отдельно проверил интеграцию с `GameScene`:
временно прописал тестовый `LevelData` в `customLevels.ts`, перезапустил
уровень — выход и зона патруля собаки в игре встали ровно там, где были
расставлены в редакторе (координата в координату), затем откатил тестовую
запись обратно на пустую таблицу.

## Фикс кликабельности уступов + живая подсветка сетки + понятное «сохранить»

Пользователь после первого использования редактора: «уступы почему-то очень
плохо кликабельны и перетаскиваются в очень редких случаях. сетка должна
показывать куда можно ставить уступ чтобы герои могли под ним проходить и
допрыгивать до соседнего» + «и ещё не ясно как сохранять сделанные уровни».
Три отдельные, но связанные правки.

**Причина плохой кликабельности.** Уступ в редакторе был
`Phaser.GameObjects.Container` с двумя дочерними `Image` и кастомной
hit-area (`container.setInteractive(new Phaser.Geom.Rectangle(...),
Phaser.Geom.Rectangle.Contains)`) — синтаксически стандартный паттерн из
документации Phaser, но на практике недостаточно надёжный. Заменил на
цельный спрайт: новая текстура-плейсхолдер `TEX.ledge` (64×32,
`PreloadScene.makeLedgePlaceholder` — визуально всё ещё два тайла с
разделительной линией) и один `Phaser.GameObjects.Image` на уступ, самый
проверенный путь в Phaser (hit-area из реальных границ текстуры, без
кастомной геометрии). Проверил именно то, что было сломано: диспатчнул
настоящий `PointerEvent('pointerdown')` в вычисленные экранные координаты
уступа (через `canvas.getBoundingClientRect()` и коэффициент масштаба
FIT-режима) — `scene.selected` корректно принял выбранный уступ. Полный
drag синтетическими событиями через `javascript_tool` не завёлся стабильно
(отдельная, уже известная проблема воспроизведения реального pointer capture
в этом окружении, см. выше) — сам механизм `setDraggable` не переписывался,
это встроенный Phaser API.

**Живая подсветка сетки.** Новая `updateDragPreview()` в `EditorScene`:
пока уступ (или ещё не отпущенный «штамп» из палитры) тащится, на клетку
под курсором рисуется рамка — зелёная, если туда можно ставить, красная,
если нет. Проверка на месте использует те же чистые функции, что и
«Проверить уровень»: `ledgesTooClose` (не пересекается с соседями),
`isLedgeReachableFrom` (новая — допрыгиваемо от БЛИЖАЙШЕГО уже
поставленного уступа, та же физика `isReachableAtGap`) и `hasHeadroomBelow`
(новая — запас по высоте: ближайшая поверхность ниже, с которой уступ
пересекается по X, должна отстоять минимум на `PLAYER.height`, иначе герой,
идущий понизу, застрянет головой). `hasHeadroomBelow` попала и в
`validateLevel` целиком — новое поле `noHeadroom` в
`LevelValidationResult`.

**Неожиданное:** свой же новый тест `validateLevel` против настоящего
уровня из процедурного генератора упал на `noHeadroom` — генератор строит
одну цепочку прыжков, а не структуру для хождения понизу, гарантии запаса
по высоте под уступом никогда не было в его контракте. Не стал ретрофитить
генератор (риск для уже задеплоенного, протестированного кода ради
проверки, которая для его дизайна нерелевантна) — поправил тест: он
по-прежнему требует от генератора допрыгиваемость/отсутствие
пересечений/границы экрана, но не headroom. `noHeadroom` — требование
только для редактора, где дизайнер может специально строить проходы понизу.

**«Как сохранять».** Раньше «Экспорт» клал JSON в консоль и буфер обмена —
неочевидно, а `navigator.clipboard.writeText` вдобавок реально падает, если
документ не в фокусе (сам поймал `Document is not focused` при тестировании
через `javascript_tool` — то есть это не только грабли автоматизации, а
хрупкость самого экспорта). Заменил на кнопку «Скачать»: собирает
`customLevels.ts` ЦЕЛИКОМ (все уровни с черновиком в `localStorage`,
объединённые с уже существующей `CUSTOM_LEVELS`) и скачивает как файл через
`Blob` + временный `<a download>` — не зависит от фокуса окна и не требует
буфера обмена. Пользователю нужно просто заменить им
`src/config/customLevels.ts` в репозитории. На загрузке сцены теперь
показывается инструкция подольше (4.5с): «Тащи уступ на сетку → «Проверить»
→ «Скачать» → замени customLevels.ts в репозитории».

**Проверено:** `npm run typecheck`, `npm run lint`, `npm test` (110/110,
`levelValidation.test.ts` вырос до 19 тестов — новые для `hasHeadroomBelow`
и `isLedgeReachableFrom`), `npm run build`. Клик по уступу — настоящим
диспатчнутым `PointerEvent` в вычисленные координаты (не вызовом метода
напрямую — так и был бы не пойман реальный баг). Подсветка сетки — прямым
вызовом `updateDragPreview` с координатами, для которых заранее руками
посчитал ожидаемый результат физики (нашёл и объяснил не баг, а верно
пойманный «слишком близко» кейс на 30px зазоре при минимуме 32px). Кнопка
«Скачать» — перехватил `Blob`/`<a>.click()` в тесте, прочитал сгенерированный
файл, ЗАМЕНИЛ им реальный `src/config/customLevels.ts` и прогнал
`npm run typecheck` — компилируется как есть, затем откатил обратно на
пустую таблицу.

## «Играть» в редакторе и WYSIWYG-сетка

**Вопрос пользователя:** «почему рыбки ставятся не над уступами, а
наползают? я не понял, как начать играть в сделанный уровень». Два разных
дефекта, оба про то, что редактор показывает не то, что получится.

**Наползание — три причины, а не одна.**

1. Сетка рисовалась от `toolbarHeight` (линии 26, 58, 90…), а объекты
   снапились к кратным `tileSize` от нуля. Две разные решётки со сдвигом
   6px: глазу не за что зацепиться, всё «мимо клеток». Теперь сетка
   рисуется по той же решётке, что и снап, плюс отдельная линия по верху
   пола.
2. Рыбка и выход снапились в **угол** клетки, а рисуются с origin по
   центру (рыбка) и по низу (выход) — половина спрайта уезжала в соседнюю
   клетку и утопала в уступе. Теперь точечные объекты снапятся по своему
   origin: рыбка — в центр клетки, выход — нижней гранью.
3. Клетку под курсором мало снапнуть — надо понимать, занята ли она.
   Рыбка, брошенная на уступ, теперь встаёт вплотную **над** ним, выход —
   нижней гранью на его верх (та же конвенция, что у процедурного
   генератора: `exit.y === ledge.topY`).

Отдельно чинился кламп: границы округлялись не по клеткам, и уступ,
доведённый до края, вставал на `y = 26` или `296` — то есть мимо решётки
навсегда. Старые черновики с такими координатами так и лежат криво, пока
их не перетащишь — поэтому проверка «клетка занята уступом» сделана
пересечением прямоугольников, а не сравнением координат: первая версия
через `topY === row * T` на реальном (кривом) черновике не сработала, и
рыбка снова утонула в платформе. Поймано в браузере, а не в голове.

**Выход уезжал на тайл вниз.** `setExit` рисовал спрайт с origin (0.5, 1)
в точке `y`, а сохранял `y + T`. В редакторе выход стоял на уступе, в игре
— на тайл ниже. Разошлось бы молча: `GameScene` рисует ровно то, что
записано. Теперь сохраняется нарисованная координата.

**«Играть».** Раньше сыграть в свой уровень можно было только так:
«Скачать» → положить файл в репозиторий → пересобрать. Кнопка «Играть»
запускает `GameScene` с уровнем прямо из памяти (`GameSceneData.testLevel`,
приоритет выше `CUSTOM_LEVELS`). Режим пробы намеренно изолирован от
игрока: `persist()` — no-op (иначе проверка уровня перезаписывала бы
реальный прогресс), смерть перезапускает пробу вместо `GameOver`, ESC и
достигнутый выход возвращают в редактор с тостом, HUD подписан
`[проба · ESC — в редактор]`.

**Проверено:** `npm run typecheck`, `npm run lint`, `npm test` (110/110),
`npm run build`. В браузере: расстановка из палитры перетаскиванием,
проверка сохранённого черновика (`ledges 160/256`, `fish 144/240`,
`exit 304/328` — всё по решётке), «Играть» → уровень в игре выглядит
идентично редактору → выход засчитан → возврат в редактор с тостом
«Уровень пройден — выход достижим» и сохранённой доской.

**Не проверено автоматикой:** ходьба/прыжок в тест-заезде. Браузерная
панель отдаёт синтетические keydown с `keyCode: 0`, а Phaser 3 работает
именно по `keyCode` — управление отсюда не эмулируется. Прохождение
проверялось выходом, поставленным на старте Пушка; сам путь ногами до
выхода нужно прощёлкать руками.
