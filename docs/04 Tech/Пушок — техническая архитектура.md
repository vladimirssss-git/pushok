# Пушок — техническая архитектура

Родитель: [[Пушок — MOC]]

## Стек

TypeScript + Phaser 3 + Vite. Без бэкенда, прогресс в `localStorage`.
Деплой — статика на GitHub Pages, автоматически при пуше в `main` (см. «Как
задеплоить на прод» — с 2026-08-06 ручной шаг `gh workflow run` не нужен).

## Структура

```
src/main.ts       — конфиг Phaser и регистрация сцен
src/config/       — все числа игры
src/scenes/       — Boot → Preload → Menu → Game → GameOver / Victory; Editor — dev-инструмент по ?editor
src/entities/     — Pushok и прочие объекты
src/systems/      — чистая логика: движение, прогрессия, сейв, генерация и валидация уровней
test/             — vitest на чистую логику
```

## Три правила, которые легко нарушить

1. **Числа только в `src/config/`.** Инлайновая константа в сцене невозможна для
   тюнинга и молча расходится с дизайн-заметкой.
2. **Логика — чистыми функциями в `src/systems/`.** Всё, что зашито в `update()`,
   не тестируется и переписывается при каждой смене сцены.
3. **Ключи ассетов — только из `src/config/assets.ts`.** Опечатка в строковом ключе
   не бросает ошибку: Phaser рисует зелёный квадрат.

## Геометрия уровня

Расстановка платформ не ставится «на глаз». Высота и дальность прыжка выводятся из
`src/config/physics.ts` в `src/systems/jumpGeometry.ts`, координаты уступов лежат в
`src/config/level.ts`, а тест `test/jumpGeometry.test.ts` сверяет одно с другим.

Причина: уступ, поднятый на пару пикселей выше прыжка, не роняет игру и ничего не
пишет в консоль — уровень просто становится непроходимым, и это замечает только
живой игрок. Первая версия уровня 1 наступила ровно на эти грабли: подъём 94 px
при высоте прыжка 78.9 px.

Уровень строится на 70% от предельных значений (`SAFETY_FACTOR`): предел достижим
только при идеальном вводе, и уровень на пределе играется как сломанный.

### Высота и дальность прыжка — недостаточная проверка

`isReachable(stepUp, gap)` проверяет предел высоты и предел дальности **независимо**.
Это не гарантирует проходимость: прыжок на уступ выше исходного уровня — гонка во
времени, а не два отдельных лимита. К моменту, когда игрок горизонтально долетает
до передней грани уступа, он должен УЖЕ быть на нужной высоте — иначе врезается в
торец сбоку (bonk) и падает, даже если по отдельности stepUp ≤ maxJumpHeight и
gap ≤ maxJumpDistance выполняются.

Хуже: Arcade Physics при разрешении коллизии по углу может «поймать» игрока и
поставить его на площадку почти без запаса, задолго до её геометрического левого
края (эмпирически проверено прямым пошаговым прогоном Arcade `World.separate` —
см. devlog 2026-08-05). Это делает реальную худшую дистанцию прыжка на следующий
уступ близкой к полному шагу leftX→leftX, а не к «чистому» зазору между площадками.

Добавлена `isReachableAtGap(stepUp, gapPx)` в `jumpGeometry.ts` — считает высоту,
набранную к моменту прибытия на дистанцию `gapPx`, и сверяет её со stepUp. Уровень 1
теперь проверяется в двух сценариях: прыжок с разбега (лучший случай) и прыжок сразу
после посадки у ближнего края (`worstCaseGap()` в `config/level.ts`, худший случай).

## Уровни: процедурные и авторские

С 2026-08-06 два источника уровней, приоритет у авторского:

1. `config/customLevels.ts` — таблица `CUSTOM_LEVELS: Partial<Record<number, LevelData>>`,
   собирается вручную в `EditorScene` (`?editor`) и заменяется файлом, который
   скачивает кнопка «Скачать» (собирает все уровни разом, не по одному). Пусто
   по умолчанию.
2. Если для номера уровня записи нет — как и раньше, `systems/levelGenerator.ts`
   генерирует процедурно.

С 2026-08-06 источников три, приоритет сверху вниз:
`GameScene.create()`: `testLevel ?? CUSTOM_LEVELS[level] ?? generateLevel(level)`,
где `testLevel` — уровень, переданный кнопкой «Играть» прямо из памяти
редактора (`GameSceneData.testLevel`), чтобы сыграть в свой уровень без
замены `customLevels.ts` и пересборки.

**Режим пробы изолирован от игрока.** Пока `testLevel` не null: `persist()`
— no-op (иначе проверка уровня перезаписывала бы реальный прогресс),
смерть перезапускает ту же пробу вместо `GameOver`, ESC и достигнутый
выход возвращают в `EditorScene` c номером уровня и результатом
(`playResult: 'win' | 'quit'` → тост). Это единственное место, где
`GameScene` не пишет сейв — если добавляется новая запись в `localStorage`,
её тоже надо провести через `persist()` или явно погасить в пробе.

**Общий источник проверки проходимости.** `systems/levelValidation.ts` —
`ledgesTooClose` (пересечение уступов), `hasHeadroomBelow` (запас по высоте
пройти под уступом — минимум `PLAYER.height` до ближайшей поверхности
снизу, с которой уступ пересекается по X), `isLedgeReachableFrom`
(допрыгиваемость от одной конкретной точки — для живой подсветки при
перетаскивании) и `validateLevel` (все проверки разом для целого уровня).
Генератор использует только `ledgesTooClose` вместо своей копии — headroom
для него не гарантирован и не требуется: генератор строит одну цепочку
прыжков, а не структуру для хождения понизу (см. devlog [[2026-08-06]],
раздел про фикс кликабельности). Редактор использует `validateLevel`
целиком для «Проверить уровень» и `hasHeadroomBelow`/`isLedgeReachableFrom`
для живой подсветки клетки под курсором во время перетаскивания. Важно:
`validateLevel` проверяет допрыгиваемость в порядке **массива**, не по
возрастанию X — процедурная цепочка зигзагует влево-вправо, сортировка по
X ломает реальный порядок прыжков.

`EditorScene` — Phaser-сцена, не отдельный инструмент: те же текстуры,
`tileSize`, физика прыжка. Уступ — цельный спрайт `Image` на текстуре
`TEX.ledge` (64×32-плейсхолдер из `PreloadScene`), а не `Container` с двумя
дочерними тайлами и кастомной hit-area — тот вариант ненадёжно ловил
клик/драг на практике (задокументировано, но не объяснено физически —
подозрение на Container-специфичные тонкости хит-тестинга в Phaser 3,
см. devlog [[2026-08-06]]). Палитра-«штампы» (drag создаёт объект, не
расходует источник), снап к сетке (`snapToGrid`), зона патруля собаки —
две перетаскиваемые ручки. Черновик каждого уровня — `localStorage`,
ключ `pushok:editor-draft` (отдельно от игрового `pushok:save`).

**Инвариант редактора: одна решётка и WYSIWYG** (введён 2026-08-06 после
бага «рыбки наползают на уступы»). Три правила, которые легко нарушить
снова:

1. Сетка рисуется по той же решётке, к которой снапятся объекты —
   кратные `tileSize` от нуля, а не от высоты тулбара. Любая своя система
   координат для отрисовки сетки = визуальный сдвиг относительно снапа.
2. Границы клампа округляются **по клеткам** (`FIRST_ROW`/`LAST_ROW`/
   `LAST_COL`), а не по пикселям. Кламп «до `FLOOR_TOP_Y - T`» ставил
   уступ на `y = 296` — мимо решётки навсегда.
3. Точечные объекты снапятся **по своему origin**, а не углом клетки:
   рыбка (origin по центру) — в центр клетки, выход (origin 0.5, 1) —
   нижней гранью. И то, что нарисовано, ровно то и уходит в `LevelData`:
   `GameScene` рисует эти координаты тем же origin, любой сдвиг при
   сохранении расходится молча.

**Как уровень становится дефолтным для всех (2026-08-07).** Кнопка
«Сохранить» шлёт `POST /__save-levels` на дев-сервер; плагин
`pushok-level-saver` (`vite.config.ts`, `apply: 'serve'`) пишет
`src/config/customLevels.ts`. Дальше — обычный коммит и деплой: игра
статическая, без бэкенда, поэтому «для всех игроков» физически означает
«лежит в репозитории и выкачено».

Эндпоинт пишет в исходники, поэтому у него две границы, и обе обязательны:

1. **Только локальный источник.** Проверяется `Origin` (а если его нет —
   `Host`): localhost/127.0.0.1. Без этого любая открытая в браузере
   страница могла бы переписать файл в репозитории — тот же класс дыры, что
   в advisory про CORS дев-сервера Vite, который висит в аудите зависимостей.
2. **Содержимое генерируется на сервере, а не приходит в запросе.** Тело —
   это данные (`{номер: LevelData}`), они проходят `parseLevelsPayload`
   (строгая проверка формы, номера 1..`MAX_LEVEL`, только конечные числа), и
   уже из разобранного объекта `renderCustomLevelsFile` собирает текст файла
   поле за полем. Прислать «файл целиком» нельзя — иначе POST на localhost
   означал бы запись произвольного кода в исходник.

`src/systems/levelsFile.ts` — общий чистый модуль для этого: им пользуется
и редактор (генерация файла при откате на скачивание), и плагин. Импорты
внутри него только относительные: `vite.config.ts` собирается esbuild'ом
без алиаса `@`. Покрыт `test/levelsFile.test.ts`.

**Схема `LevelData` расширяется только опциональными полями.** Черновики
редактора лежат в `localStorage` как сырой JSON без версии и миграций (в
отличие от игрового сейва) — новое обязательное поле молча сломало бы все
уже сделанные уровни. Так добавлены шипы 2026-08-07: `spikes?:
{x, y}[]`, читается как `data.spikes ?? []`. Если понадобится поле, без
которого уровень не имеет смысла, — это уже повод завести версию черновика
и миграцию, а не `?`.

Занятость клетки уступом (`ledgeAtCell`) проверяется **пересечением
прямоугольников**, а не равенством координат — черновики, сделанные до
этого фикса, лежат не по решётке, и сравнение `topY === row * T` их не
находит.

## Мобильный ввод

Схема с 2026-08-09 — плавающий стик, см. [[Пушок — мобильное управление плавающим стиком]].
Левая половина канваса: стик рождается там, где опустился палец, и подтягивается
за ним, если тот ушёл дальше `maxRadius`. Правая половина: прыжок тапом в любом
месте. Целиться некуда, поэтому промахнуться нечем — до этого были три круглые
кнопки, и мелкая мишень была главной претензией.

- `src/systems/touchStick.ts` — чистая математика (зона касания, знак направления,
  ре-центрирование базы, обрезка шляпки). Без Phaser и **без импорта конфига**:
  пороги приходят параметрами, поэтому `test/touchStick.test.ts` проверяет
  поведение, а не текущие настройки.
- `src/systems/touchControls.ts` — слой Phaser: подписка, отрисовка, вибрация.
  Публичный контракт (`direction`, `consumeJumpPress()`, `isTouchDevice()`) тот же,
  что был у геймпада, поэтому сцены при переходе на стик не менялись.
- `src/config/controls.ts` — `TOUCH_STICK` (мёртвая зона, радиусы, доля экрана,
  `hapticJumpMs`) и `TOUCH_HINT_POSITIONS` (полупрозрачные иконки до первого
  касания; это подсказки, а не мишени).

**Слушаем указатели сцены, а не игровые объекты.** `pointerdown` на объекте
приходит, только если палец опустился внутрь него: вести палец между
направлениями без отрыва невозможно, а отпускание за пределами объекта теряется —
кнопка залипала, и Пушок уходил в шипы сам. Поэтому подписка идёт на
`scene.input` (включая `POINTER_UP_OUTSIDE`) с разбором по `pointer.id`.

**Два обязательных снятия состояния.** Отписка на `Scenes.Events.SHUTDOWN` —
`GameScene` пересоздаётся после смерти, и без неё слушатели копятся, а один тап
считается за несколько прыжков. Сброс на `Core.Events.BLUR` — свёрнутая вкладка с
зажатым пальцем иначе оставляет Пушка бегущим.

`main.ts` увеличивает `input.activePointers` до 3 — без этого Phaser не даст
держать «идти» и «прыжок» одновременно (два касания разом). `index.html` —
`touch-action: none`, чтобы тач по канвасу не скроллил и не зумил страницу, плюс
оверлей «Поверни телефон» на чистом CSS
(`@media (orientation: portrait) and (pointer: coarse)`; `pointer: coarse` не даёт
ему выскочить на десктопе в узком окне). `Scale.FIT` оставлен осознанно:
`Scale.ENVELOP` обрезал бы края уровня и изменил бы то, что видит игрок.

**`?touch` в URL** принудительно включает тач-управление (по образцу `?editor`).
Без флага стик нельзя проверить в десктопном браузере: мышь шлёт те же события,
но `device.input.touch` там false, и управление просто не создаётся.

## Сейв

Схема версионирована (`SAVE_VERSION`). Меняешь структуру — пиши миграцию в
`src/systems/save.ts`, иначе у всех, кто уже играл, прогресс исчезнет без ошибки в консоли.

## CI

- `ci.yml` — typecheck, lint, tests, build на каждый push (любая ветка) и PR в main.
- `deploy-pages.yml` — **с 2026-08-06 запускается автоматически на push в `main`**
  (`on: push: branches: [main]`, плюс `workflow_dispatch` как запасной ручной путь).
  `VITE_BASE` подставляется из имени репозитория. Внутри та же проверка
  (`typecheck && test`) перед сборкой — сломанный код на прод не уедет.

## Как задеплоить на прод

1. `git push origin main` — дальше всё автоматически: workflow сам собирает,
   гоняет тесты и деплоит на Pages.
2. Проверить: `gh run list --workflow=deploy-pages.yml -L1` и сайт
   https://vladimirssss-git.github.io/pushok/.

**Грабли «на проде ничего не поменялось» (2026-08-06):** после успешного
деплоя пользователь видел старую версию (шипы, собака не прыгает). Деплой
был ни при чём — GitHub Pages отдаёт `index.html` и JS-бандл с
`cache-control: max-age=600` (10 минут), сервис-воркера в проекте нет. Браузер
может показывать закэшированную версию до 10 минут после деплоя, если
страница уже была открыта раньше. Проверка «деплой реальный, а не кэш»: имя
JS-файла — хэш от содержимого (Vite), плюс можно свериться напрямую —
`curl -s <URL>/assets/index-XXXX.js | grep '<строка_из_нового_кода>'`.
Если строка есть — деплой в порядке, дело в кэше браузера (жёсткое
обновление `Cmd/Ctrl+Shift+R` или приватное окно).

`gh workflow run`). Источник: пользователь — «давай исправим блокировку чтобы
сборка шла автоматом».

Причина блокировки `git push origin main` из Claude Code (задокументированная

[[2026-08-06]]).

Второй шаг ручного вмешательства — `gh workflow run deploy-pages.yml` — был
нужен только потому, что триггер был `workflow_dispatch`-only. Добавлен
`push: branches: [main]` — деплой теперь следует за пушем без агента.

Компромисс: агент (и любой, у кого есть доступ push в main) теперь может
задеплоить на прод одним `git push`, без второго подтверждающего шага. Откат
при необходимости — вернуть `"Bash(git push origin main:*)"` в `deny` и/или
убрать `push:` из триггера `deploy-pages.yml`.

## Смоук в браузерной панели: что проверяется, а что нет

Ограничение переоткрывалось три раза подряд (devlog [[2026-08-05]],
[[2026-08-06]]), поэтому зафиксировано здесь как правило, а не как
наблюдение дня. **2026-08-09 переоткрыто в четвёртый раз** — сначала
клавишами панели, потом синтетическим `KeyboardEvent`. Читать этот раздел
до того, как лезть проверять ввод, а не после.

**Не работает: управление игрой с клавиатуры.** Браузерная панель отдаёт
синтетические `keydown` с `keyCode: 0`, а Phaser 3 диспетчеризует клавиши
именно по `keyCode` — ни одиночное нажатие, ни удержание до игры не
доходят. Ручной `dispatchEvent` с подменённым `keyCode` через
`Object.defineProperty` тоже не оживляет ввод. Отдельно: если
`document.visibilityState === 'hidden'`, игровой цикл вообще стоит —
проверять это первым делом, прежде чем искать баг в игре.

**Работает и должно использоваться:** мышь/тач (`left_click`,
`left_click_drag`) — drag-n-drop редактора, кнопки, тап-старт меню;
чтение `localStorage` через `javascript_tool` (единственный надёжный
способ проверить, что реально сохранилось); скриншоты для
геометрии/выравнивания; консоль и сетевые запросы.

**Как проверять тач-управление (2026-08-09).** Два условия, без любого из
них проверка молча показывает «ничего не происходит»:

1. Открывать с **`?touch`** в URL. На десктопе `device.input.touch` равен
   false, и `TouchControls` не создаётся вовсе — проверять нечего.
2. Слать **`MouseEvent`** (`mousedown`/`mousemove`/`mouseup`) на канвас, а
   не `PointerEvent`. Phaser 3 слушает mouse-события; синтетические
   `PointerEvent` до игры не доходят и не дают никакой диагностики.

Координаты пересчитывать из логических в клиентские через
`canvas.getBoundingClientRect()`: `clientX = rect.left + x * rect.width / 640`.
Так проверяются рождение стика под пальцем, ре-центрирование базы,
направление и снятие состояния на отпускании. **Мультитач так не
проверяется** — два одновременных касания мышью не изобразить.

**Как проверять геймплей, который требует клавиатуры:** свести сценарий к
состоянию, наблюдаемому без ввода. Пример 2026-08-06: чтобы проверить
возврат из тест-заезда в редактор, выход ставился прямо на старте Пушка —
оверлап срабатывал в первом же кадре. Путь ногами до выхода всё равно
остаётся ручным смоуком.
